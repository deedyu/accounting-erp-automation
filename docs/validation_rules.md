# 분개장 오류 검증 규칙

## 1. 문서 목적

본 문서는 회계 분개장 ERP 입력 검증 자동화 시스템에 적용한 오류 판정 기준과 처리 방법을 정리한 문서이다.

검증 프로그램은 엑셀 분개장의 각 전표를 검사한 후 다음 두 가지 상태로 분류한다.

| 처리 상태 | 판정 기준 |
|---|---|
| 입력 가능 | 탐지된 오류가 없는 전표 |
| 검토 필요 | 하나 이상의 오류가 탐지된 전표 |

오류가 발견된 전표는 ERP 업로드 대상에서 제외한다. 담당자는 검토 대기열에서 오류 내용을 확인하고 원본 데이터를 수정한다.

---

## 2. 검증 처리 순서

분개장 검증은 다음 순서로 진행한다.

1. 원본 분개장과 기준정보 파일을 불러온다.
2. 필수값 누락 여부를 검사한다.
3. 거래처 코드를 검사한다.
4. 부서 코드를 검사한다.
5. 계정과목 코드를 검사한다.
6. 차변·대변 합계를 검사한다.
7. 전표 총금액을 검사한다.
8. 부가세 금액을 검사한다.
9. 증빙번호 중복 여부를 검사한다.
10. 거래일자의 회계기간 포함 여부를 검사한다.
11. 발견한 오류를 저장한다.
12. 입력 가능 전표와 검토 필요 전표를 분리한다.
13. 예상 오류와 실제 탐지 결과를 비교한다.

검증 로직은 `src/journal_validator.py`에서 실행한다.

---

## 3. 필수값 누락 검사

### 검사 목적

ERP 입력에 필요한 값이 비어 있는 전표를 찾는다.

### 주요 검사 대상

| 컬럼명 | 설명 |
|---|---|
| voucher_id | 전표번호 |
| transaction_date | 거래일자 |
| department_code | 부서 코드 |
| partner_code | 거래처 코드 |
| evidence_type | 증빙 유형 |
| evidence_no | 증빙번호 |
| description | 거래 적요 |
| debit_account_1 | 첫 번째 차변 계정과목 |
| debit_amount_1 | 첫 번째 차변 금액 |
| credit_account_1 | 첫 번째 대변 계정과목 |
| credit_amount_1 | 첫 번째 대변 금액 |
| total_amount | 전표 총금액 |

### 판정 조건

필수 컬럼의 값이 다음 중 하나에 해당하면 오류로 판단한다.

- `NaN` 또는 `None`
- 빈 문자열
- 공백만 입력된 문자열

### 오류 결과

| 항목 | 값 |
|---|---|
| error_type | 필수값 누락 |
| column | 값이 누락된 컬럼 |
| detail 예시 | `evidence_no: 값 누락` |

## 4. 거래처 기준정보 검사

### 검사 목적

분개장에 입력된 거래처 코드가 거래처 기준정보에 등록되어 있는지 확인한다.

### 기준 파일

`data/master/vendors.csv`

### 검사 대상

`partner_code`

### 판정 조건

분개장의 `partner_code`가 거래처 기준정보의 `partner_code` 목록에 없으면 오류로 판단한다.

### 오류 결과

| 항목 | 값 |
|---|---|
| error_type | 존재하지 않는 거래처 |
| column | partner_code |
| detail 예시 | `V999: 거래처 기준표에 없음` |

분개장에 입력된 부서 코드가 부서 기준정보에 등록되어 있는지 확인한다.

### 기준 파일

`data/master/departments.csv`

### 검사 대상

`department_code`

### 판정 조건

분개장의 `department_code`가 부서 기준정보의 `department_code` 목록에 없으면 오류로 판단한다.

### 오류 결과

| 항목 | 값 |
|---|---|
| error_type | 존재하지 않는 부서 |
| column | department_code |
| detail 예시 | `D999: 부서 기준표에 없음` |

## 6. 계정과목 기준정보 검사

### 검사 목적

차변과 대변에 입력된 계정과목 코드가 계정과목 기준정보에 등록되어 있는지 확인한다.

### 기준 파일

`data/master/accounts.csv`

### 검사 대상

- `debit_account_1`
- `debit_account_2`
- `credit_account_1`
- `credit_account_2`

### 판정 조건

값이 입력된 계정과목 코드가 기준정보의 `account_code` 목록에 없으면 오류로 판단한다.

두 번째 차변·대변 계정과목은 선택 항목이므로 값이 비어 있으면 검사에서 제외한다.

### 오류 결과

| 항목 | 값 |
|---|---|
| error_type | 존재하지 않는 계정과목 |
| column | 오류가 발견된 계정과목 컬럼 |
| detail 예시 | `9999: 계정과목 기준표에 없음` |

## 7. 차변·대변 일치 검사

### 검사 목적

복식부기의 기본 원칙에 따라 전표의 차변 합계와 대변 합계가 일치하는지 확인한다.

### 계산식

- 차변 합계 = `debit_amount_1 + debit_amount_2`
- 대변 합계 = `credit_amount_1 + credit_amount_2`

두 번째 차변 또는 대변 금액이 비어 있으면 0원으로 계산한다.

### 판정 조건

`차변 합계 != 대변 합계`

위 조건에 해당하면 오류로 판단한다.

### 오류 결과

| 항목 | 값 |
|---|---|
| error_type | 차변·대변 불일치 |
| column | debit_amount_1 |
| detail 예시 | `차변 670,000원 / 대변 660,000원` |

---

## 8. 전표 총금액 검사

### 검사 목적

전표에 입력된 총금액과 실제 분개 금액 합계가 일치하는지 확인한다.

### 계산식

분개 합계는 다음과 같이 계산한다.

`분개 합계 = debit_amount_1 + debit_amount_2`

### 판정 조건

차변 합계와 대변 합계가 일치한 상태에서 다음 조건을 검사한다.

`total_amount != 분개 합계`

### 검사 순서

차변과 대변이 일치하지 않는 전표는 먼저 `차변·대변 불일치`로 분류한다.

하나의 금액 문제를 `차변·대변 불일치`와 `전표 합계 불일치`로 중복 표시하지 않도록 `elif` 조건을 사용한다.

### 오류 결과

| 항목 | 값 |
|---|---|
| error_type | 전표 합계 불일치 |
| column | total_amount |
| detail 예시 | `입력 5,400,000원 / 분개 5,500,000원` |

---

## 9. 부가세 계산 검사

### 검사 목적

과세 거래의 입력 부가세가 공급가액의 10%와 일치하는지 확인한다.

### 검사 대상

- `supply_amount`
- `vat_amount`

### 적용 조건

공급가액이 0원보다 큰 거래만 검사한다.

`supply_amount > 0`

### 예상 부가세 계산식

`예상 부가세 = round(supply_amount × 0.1)`

### 판정 조건

`vat_amount != 예상 부가세`

### 오류 결과

| 항목 | 값 |
|---|---|
| error_type | 부가세 계산 오류 |
| column | vat_amount |
| detail 예시 | `입력 100,000원 / 예상 150,000원` |

### 제한사항

현재 검증 규칙은 일반적인 부가세율 10%를 기준으로 한다.

면세, 영세율, 세액 조정 및 업종별 예외 규칙은 현재 범위에 포함하지 않는다.

---

## 10. 증빙번호 중복 검사

### 검사 목적

동일한 증빙번호가 여러 전표에서 중복으로 사용되었는지 확인한다.

### 검사 대상

`evidence_no`

### 판정 조건

- 증빙번호가 비어 있지 않아야 한다.
- 동일한 증빙번호가 처음 등장한 거래는 정상으로 처리한다.
- 동일한 증빙번호가 두 번째 이후에 등장하면 오류로 처리한다.

### 처리 방식

`journal["evidence_no"].notna() & journal["evidence_no"].duplicated(keep="first")`

### 오류 결과

| 항목 | 값 |
|---|---|
| error_type | 증빙번호 중복 |
| column | evidence_no |
| detail 예시 | `CARD-202608-0001: 중복 증빙` |

증빙번호가 없는 전표는 중복 검사에서 제외하고 `필수값 누락` 규칙에서 처리한다.

---

## 11. 회계기간 검사

### 검사 목적

거래일자가 대상 회계기간에 포함되는지 확인한다.

### 대상 회계기간

- 시작일: `2026-08-01`
- 종료일: `2026-09-01`
- 종료일은 정상 범위에 포함하지 않는다.

정상 거래일자의 범위는 `2026-08-01 이상, 2026-09-01 미만`이다.

### 판정 조건

다음 중 하나에 해당하면 오류로 판단한다.

- `transaction_date < 2026-08-01`
- `transaction_date >= 2026-09-01`

### 오류 결과

| 항목 | 값 |
|---|---|
| error_type | 회계기간 이탈 |
| column | transaction_date |
| detail 예시 | `2026-09-05: 회계기간 아님` |

거래일자는 `pandas.to_datetime()`을 사용해 날짜 자료형으로 변환한다.

## 12. 오류 저장 구조

탐지된 오류는 다음 구조로 저장한다.

| 컬럼명 | 설명 |
|---|---|
| voucher_id | 오류가 발생한 전표번호 |
| column | 오류가 발생한 컬럼 |
| error_type | 오류 유형 |
| detail | 담당자가 확인할 오류 상세 내용 |

한 전표에서 서로 다른 오류가 여러 개 발견되면 오류별로 행을 나누어 저장한다.

차변·대변 불일치와 전표 합계 불일치는 같은 금액 문제의 중복 안내를 막기 위해 우선순위를 적용한다.

---

## 13. 상세 메시지 작성 기준

검토 대기열을 쉽게 확인할 수 있도록 상세 메시지는 짧은 명사형 표현으로 작성한다.

### 작성 원칙

- `~입니다`, `~했습니다`와 같은 긴 문장형 표현을 사용하지 않는다.
- 오류값과 기준값을 함께 표시한다.
- 금액에는 천 단위 구분기호와 원 단위를 표시한다.
- 담당자가 원인을 바로 확인할 수 있도록 핵심 내용만 작성한다.

### 예시

| 긴 표현 | 적용 표현 |
|---|---|
| `9999 코드는 계정과목 기준표에 없습니다.` | `9999: 계정과목 기준표에 없음` |
| `증빙번호가 중복됐습니다.` | `CARD-202608-0001: 중복 증빙` |
| `evidence_no 값이 입력되지 않았습니다.` | `evidence_no: 값 누락` |
| `2026-09-05는 회계기간에 포함되지 않습니다.` | `2026-09-05: 회계기간 아님` |

## 14. 처리 상태 판정

전표별 오류 건수를 기준으로 처리 상태를 결정한다.

- 오류 수가 0건이면 `입력 가능`으로 분류한다.
- 오류 수가 1건 이상이면 `검토 필요`로 분류한다.

### 입력 가능

- ERP 업로드용 CSV 변환 대상
- ERP 연계용 JSON 변환 대상
- SQLite의 ERP 전표 및 분개 행 테이블 적재 대상

### 검토 필요

- ERP 업로드 대상에서 제외
- 검토 대기열에 저장
- Tableau 대시보드에 오류 유형과 상세 내용 표시
- 담당자가 원본 데이터를 확인하고 수정

시스템은 오류가 있는 전표를 임의로 수정하거나 자동으로 승인하지 않는다.

## 15. 검증 결과 비교 기준

의도적으로 오류를 삽입한 정답 데이터와 실제 탐지 결과를 비교한다.

### 평가 구분

| 구분 | 설명 |
|---|---|
| 정상 탐지 | 예상 오류와 탐지 오류가 일치한 경우 |
| 미탐지 | 예상 오류를 탐지하지 못한 경우 |
| 추가 탐지 | 예상하지 않은 오류를 추가로 탐지한 경우 |

### 평가 지표

- 정밀도 = 정상 탐지 수 ÷ 전체 탐지 수
- 재현율 = 정상 탐지 수 ÷ 전체 예상 오류 수

### 가상 데이터 검증 결과

| 지표 | 결과 |
|---|---:|
| 전체 전표 | 500건 |
| 예상 오류 | 50건 |
| 탐지 오류 | 50건 |
| 정상 탐지 | 50건 |
| 미탐지 | 0건 |
| 추가 탐지 | 0건 |
| 정밀도 | 100.0% |
| 재현율 | 100.0% |

위 수치는 사전에 정의한 오류를 삽입한 가상 데이터의 테스트 결과이다.

실제 운영 환경에서 발생할 수 있는 모든 회계 오류를 탐지한다는 의미는 아니다.

## 16. ERP 변환 후 최종 검사

입력 가능 전표를 ERP 행 구조로 변환한 뒤 다음 항목을 다시 확인한다.

| 검사 항목 | 정상 조건 |
|---|---|
| 차변·대변 균형 | 전표별 차변 합계와 대변 합계가 일치 |
| 분개 순번 | 동일 전표 안에서 행 순번이 중복되지 않음 |
| 계정 연결 | 모든 분개 행에 유효한 계정과목 코드가 존재 |
| 전표 제외 | 검토 필요 전표가 ERP 업로드 결과에 포함되지 않음 |

가상 대량 데이터의 변환 결과는 다음과 같다.

| 항목 | 결과 |
|---|---:|
| ERP 입력 가능 전표 | 450건 |
| ERP 분개 행 | 1,350건 |
| 차변·대변 불일치 | 0건 |
| 중복 순번 | 0건 |
| 계정 연결 실패 | 0건 |

## 18. 현재 검증 범위의 한계

현재 프로젝트는 포트폴리오용 가상 제조기업의 분개장을 대상으로 한다.

현재 검증 범위에는 다음과 같은 제한이 있다.

- 2026년 8월 회계기간을 기준으로 검사한다.
- 일반 과세 거래에 부가세율 10%를 적용한다.
- 원본 분개장은 최대 차변 2개와 대변 2개의 구조를 사용한다.
- 실제 ERP 시스템과 직접 연결하지 않는다.
- 오류 전표를 자동으로 수정하거나 승인하지 않는다.
- 실제 기업의 내부회계관리제도와 승인 절차를 적용하지 않는다.
- 면세, 영세율 및 복잡한 세무 예외 규칙을 포함하지 않는다.

실제 운영 환경에 적용하려면 회계기간 설정값 관리, 세금 유형별 규칙, 사용자 권한, 승인 절차, 감사 로그 및 ERP 인터페이스 규격을 추가해야 한다.
